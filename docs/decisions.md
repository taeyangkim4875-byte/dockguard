# 설계 결정 기록

dockguard를 만들면서 내린 결정과 그 이유를 남깁니다.
대부분은 **운영 중에 겪은 문제**에서 나왔고, 다르게 갈 수도 있었던 갈림길이었습니다.

## 1. 진단(diagnose)과 예방(scan)을 분리했다

### 배경

처음 만든 것은 `scan`이었습니다. 취약점을 미리 찾아 점수를 매기는, 흔한 형태의 보안 점검 도구입니다.
그런데 정작 제가 며칠을 썼던 상황은 **"이미 장애가 났고, 원인을 모르겠다"**였습니다.
백엔드가 RabbitMQ에 붙지 못했고, 에러는 `Connection refused` 한 줄이었습니다.

그때 `scan`을 돌렸다면 답이 나왔을까요? 나오긴 나옵니다 — NET-001이 "공유 네트워크 없음"을 잡습니다.
하지만 **그러려면 먼저 `dependencies.yaml`에 "백엔드는 RabbitMQ에 붙어야 한다"고 선언해 뒀어야** 합니다.
장애 한가운데서 처음 도구를 집어 든 사람에게는 그 선언이 없습니다.
게다가 `scan`의 출력은 "이 호스트의 취약점 26가지"이지, "지금 이 연결이 왜 안 되는가"가 아닙니다.

### 고민한 선택지

| 선택지 | 장점 | 문제 |
|--------|------|------|
| **A. scan을 더 똑똑하게** — 네트워크 룰이 모든 컨테이너 쌍을 검사 | 명령이 하나로 유지된다 | 컨테이너 10개면 조합이 45개다. 대부분은 통신할 필요가 없는 쌍이라 노이즈가 되고, 점수 체계도 무너진다 |
| **B. 별도 명령(diagnose)** | 사용자가 증상을 입력하니 검사 범위가 정확히 두 컨테이너로 좁혀진다 | 명령과 개념이 하나 늘어난다 |
| **C. 문서로 안내** — "이럴 땐 이렇게 확인하세요" | 코드가 늘지 않는다 | 장애 중에 문서를 읽고 명령을 하나씩 치는 건 결국 사람이 하던 그 일이다 |

### 결정

**B — `dockguard diagnose connectivity <A> <B> --port <N>`를 별도 명령으로 만들었습니다.**
scan과는 데이터 모델도 분리했습니다. scan은 `Finding`(취약점)을 모으고, diagnose는 `DiagnosisStep`(검사 로그)을 쌓습니다.

### 근거

- **입력이 다릅니다.** scan은 "이 호스트"를 받고, diagnose는 "이 증상"을 받습니다. 증상을 받는 순간 검사 범위가 한 쌍으로 좁혀져, 그 쌍에 대해서만큼은 훨씬 깊게 파고들 수 있습니다(포트, icc, 환경변수의 접속 주소까지).
- **출력의 목적이 다릅니다.** scan의 결과물은 **점수와 목록**(무엇부터 고칠까), diagnose의 결과물은 **하나의 근본 원인과 근거**(지금 이걸 고치면 된다)입니다. 같은 리포터에 밀어 넣으면 둘 다 어정쩡해집니다.
- **사전 준비가 필요 없습니다.** diagnose는 선언 파일 없이 컨테이너 이름 두 개만으로 동작합니다. 장애 중에 처음 설치해도 바로 쓸 수 있어야 의미가 있습니다.
- 대신 **둘은 서로를 가리킵니다.** diagnose가 원인을 못 찾으면 마지막에 `dockguard scan --category network`를 안내하고, scan의 NET-001 설명은 diagnose로 더 파고들 수 있다고 알려 줍니다. 예방과 진단은 같은 지식(네트워크 격리, icc)을 다른 시점에 쓰는 것뿐입니다.

## 2. 자동 수정을 기본으로 하지 않았다

### 배경

"취약점을 찾아 준다"의 자연스러운 다음 단계는 "고쳐 준다"입니다. 실제로 `--fix` 한 번에 전부 고쳐 주는 도구들이 있습니다.

하지만 제가 겪은 사고의 절반은 **자동화된 조치 자체가 원인**이었습니다.
`docker compose down`은 문서대로 동작했지만 익명 볼륨과 함께 RabbitMQ 계정이 사라졌고,
`icc: false`는 벤치마크가 권장하는 올바른 설정이었지만 서비스 연결을 끊었습니다.
둘 다 "틀린 명령"이 아니라 **영향 범위를 모른 채 실행한 올바른 명령**이었습니다.

### 고민한 선택지

| 선택지 | 문제 |
|--------|------|
| **A. 전부 자동 수정** (`--fix`) | 네트워크 설정 하나가 서비스 전체를 끊을 수 있다. 되돌리려면 데몬을 또 재시작해야 하고, 그 사이 장애는 계속된다 |
| **B. 전혀 수정하지 않음** (진단 전용) | 안전하지만, `no-new-privileges: true`처럼 부작용이 거의 없는 항목까지 손으로 고치게 하는 건 게으른 설계다 |
| **C. 위험도로 나누고, 기본은 미리보기** | 구현이 복잡해진다 (룰마다 위험도 판단, 이중 확인, 롤백) |

### 결정

**C를 택하되, 세 겹의 안전장치를 두었습니다.**

1. **기본은 미리보기(dry-run).** `dockguard fix daemon`은 diff만 보여주고 파일을 건드리지 않습니다. `--apply`가 있어야 씁니다.
2. **위험도로 나눕니다.** `FixRisk.SAFE`(no-new-privileges, live-restore, log-opts)만 기본 대상이고, `RISKY`(icc, userns-remap)는 사용자가 `--rule DAEMON-001`로 **이름을 직접 적어야** 포함되며 이중 확인을 받습니다.
3. **compose 파일은 아예 수정하지 않습니다.** 서비스 의존성·볼륨 소유권·기동 순서가 얽혀 있어 한 줄 변경의 영향을 도구가 알 수 없습니다. 대신 영향받는 서비스 이름을 넣은 수정 예시 YAML을 보여줍니다.

또 **Docker를 직접 재시작하지 않습니다.** 대신 지금 상태에 맞는 순서(리로드로 live-restore를 먼저 켜고 → 재시작)를 안내합니다.

### 근거

- 자동 수정의 가치는 "시간 절약"이지만, 인프라 설정에서 **한 번의 잘못된 적용은 절약한 시간을 전부 상쇄**합니다. 비대칭적인 손실이므로 보수적으로 가는 것이 맞습니다.
- 룰은 `ConfigPatch`(무엇을 바꿀지)만 선언하고 파일 I/O는 Remediator가 전담합니다. 그래서 **어떤 룰도 백업·검증·롤백을 우회할 수 없습니다.** 룰이 늘어나도 안전장치는 한 곳에만 있습니다.
- 적용 순서는 임시 파일 검증(`dockerd --validate`) → 백업 → `os.replace`(원자적 교체)입니다. 검증에 실패하면 원본은 **전혀 건드려지지 않은 상태**로 끝나고, 교체 도중 프로세스가 죽어도 파일이 반쯤 쓰인 상태가 되지 않습니다.
- 재시작 시점은 서비스 영향을 아는 **운영자의 판단**입니다. 도구가 대신 결정할 수 있는 성질이 아닙니다.

## 3. 모든 권고에 부작용(tradeoff)을 붙였다

### 배경

`icc: false` 때문에 며칠을 썼을 때 가장 답답했던 건, **그 설정을 켜라고 한 쪽에서 아무도 "이러면 통신이 끊긴다"고 말해 주지 않았다**는 점이었습니다.
CIS 벤치마크 문서에는 각 항목에 Impact 절이 있습니다. 하지만 장애 한가운데서 PDF를 열어 해당 항목을 찾아 읽는 사람은 없습니다.

보안 점검 도구의 출력은 대개 이렇게 끝납니다.

> `[FAIL] 2.2 Ensure network traffic is restricted between containers on the default bridge`

이 줄을 보고 `icc: false`를 켠 사람이 다음 날 겪을 일에 대해서는 아무 말이 없습니다.

### 고민한 선택지

| 선택지 | 문제 |
|--------|------|
| **A. 권고만 표시** (기존 도구들) | 구현이 간단하지만, 내가 겪은 문제를 그대로 반복시킨다 |
| **B. 부작용이 큰 항목은 아예 권고하지 않음** | 보안 도구가 보안 권고를 빼는 셈이다. `icc: false`는 여전히 옳은 설정이다 |
| **C. 권고 + 부작용 + 대처법을 한 화면에** | 룰마다 긴 설명을 써야 한다. 26개 룰 × 4개 필드 = 100개가 넘는 글 |

### 결정

**C — `Finding` 모델에 `tradeoff` 필드를 두고, 룰을 추가할 때 반드시 채우게 했습니다.**
`why`(왜 위험한가) · `how_to_fix`(어떻게 고치나)와 나란히 있는 1급 필드이고, **터미널 `--explain`과 HTML 리포트 모두에서 노란 박스로 강조**됩니다.

### 근거

- 운영자가 정말 필요로 하는 건 권고가 아니라 **권고 바로 옆의 다음 문장**입니다. "icc를 끄면 기본 bridge의 통신이 끊기니, 통신이 필요한 서비스는 같은 커스텀 네트워크에 두어라" — 이 한 문장이 있었다면 저는 며칠을 아꼈을 겁니다.
- 부작용을 아는 것은 **보안 조치를 실제로 적용하게 만드는** 조건이기도 합니다. 무슨 일이 생길지 모르는 설정은 결국 아무도 켜지 않습니다.
- 부작용 정보는 자동 수정의 위험도 판단으로도 이어집니다. `tradeoff`가 큰 항목은 `FixRisk.RISKY`가 되고, 자동 수정에서 제외되거나 이중 확인을 받습니다. **설명과 동작이 같은 판단을 공유**합니다.
- 글의 양이 문제가 되지 않도록, `tests/test_content_quality.py`가 모든 룰의 설명을 실제로 렌더링해 보고 비어 있거나 깨진 Markdown을 잡아냅니다. 설명도 코드처럼 테스트합니다.

## 4. 룰을 플러그인 구조로 만들었다

### 배경

점검 항목은 계속 늘어납니다. 처음엔 3개로 시작했지만 지금은 26개이고, 앞으로도 늘 겁니다.
이때 흔한 구조는 **거대한 `if`문 하나** 또는 **중앙 등록 목록**입니다.

```python
# 이렇게 하지 않기로 했다
RULES = [IccRule(), NoNewPrivilegesRule(), LiveRestoreRule(), ...]   # 새 룰마다 여기도 고쳐야 함
```

### 고민한 선택지

| 선택지 | 문제 |
|--------|------|
| **A. 중앙 목록에 수동 등록** | 룰 추가가 파일 2곳 수정이 된다. 등록을 빠뜨리면 조용히 점검되지 않는다 (가장 나쁜 실패) |
| **B. 설정 파일(YAML)로 룰 정의** | 단순 조건은 되지만, "icc는 daemon.json과 실행 중인 bridge 옵션을 함께 본다" 같은 판단을 YAML로 쓰면 결국 YAML로 프로그래밍하게 된다 |
| **C. 파일 추가 = 자동 등록** (`@register` + 패키지 자동 import) | 임포트 부수효과에 의존한다. 룰 ID 중복 같은 실수를 막아야 한다 |

### 결정

**C — `rules/` 아래에 파일을 하나 만들고 클래스에 `@register`를 붙이면 끝입니다.**
`rules/__init__.py`가 하위 모듈을 재귀적으로 import하고, 중복 ID는 **등록 시점에 예외로 거부**합니다.
카테고리별 공통 베이스(`BooleanDaemonRule`, `ComposeRule`, `NetworkRule`)를 두어, 흔한 룰은 선언만으로 끝납니다.

### 근거

- **룰이 `ScanContext`만 본다**는 규칙이 이 구조의 핵심입니다. 룰은 Docker나 파일 시스템에 직접 접근하지 않으므로, 실제 Docker 없이 가짜 컨텍스트로 전부 테스트할 수 있습니다(단위 테스트 870여 개가 Docker 없이 돕니다).
- 엔진은 룰 하나에서 예외가 나도 **나머지를 계속 실행**하고 오류를 따로 보고합니다. 룰이 격리돼 있으니 새 룰을 추가해도 기존 점검이 멈추지 않습니다.
- 확장 지점이 정해져 있으니 **룰셋(끄기·심각도 조정)과 리포터를 룰과 무관하게** 만들 수 있었습니다. 출력 형식을 3개(터미널/HTML/JSON) 추가하는 동안 룰 코드는 한 줄도 바뀌지 않았습니다.
- 같은 구조를 진단에도 적용했습니다. `Diagnosis` 베이스 클래스가 있고, 새 진단은 `steps()` 제너레이터만 구현하면 됩니다. 검사 로그 수집·근본 원인 판정·출력은 베이스와 리포터가 처리합니다.

## 5. 진단은 첫 실패에서 멈추지 않고 검사 로그를 끝까지 남긴다

### 배경

진단 트리를 만들 때 자연스러운 구현은 **첫 실패에서 즉시 반환**입니다. 원인을 찾았으니 더 볼 이유가 없어 보입니다.

그런데 제가 겪은 사고는 원인이 **하나가 아니었습니다.**
네트워크가 분리돼 있었고(원인 1), 동시에 백엔드의 `RABBITMQ_HOST`가 호스트 외부 IP로 잡혀 있었습니다(원인 2).
네트워크만 고치고 재기동했다면 여전히 불안정했을 겁니다.

### 고민한 선택지

| 선택지 | 문제 |
|--------|------|
| **A. 첫 FAIL에서 즉시 반환** | 빠르고 단순하지만, 함께 고쳐야 할 문제를 놓친다. 고치고 다시 돌리기를 반복하게 된다 |
| **B. 모든 문제를 동등하게 나열** | 무엇이 원인이고 무엇이 곁가지인지 사용자가 다시 판단해야 한다. 그러면 도구가 한 일이 없다 |
| **C. 끝까지 검사하되, 첫 FAIL을 근본 원인으로 지목** | 뒤 단계가 의미를 잃는 경우(컨테이너가 아예 없음)를 따로 처리해야 한다 |

### 결정

**C — 검사는 끝까지 진행하고, 출력은 계층을 둡니다.**

- **근본 원인** (첫 FAIL) — 빨간 패널로 근거·해결·부작용까지
- **추가로 발견된 문제** (그 뒤의 FAIL) — 노란 패널로 "이것도 고쳐야 연결됩니다"
- 뒤 단계가 무의미해지는 경우(컨테이너가 존재하지 않음)에만 제너레이터가 거기서 멈춥니다.

첫 FAIL을 근본 원인으로 삼는 근거는 **진단 트리를 인과 순서로 배치**했기 때문입니다 (컨테이너 존재 → 포트 → 네트워크 경로 → 통신 허용 → 주소 설정). 앞 단계가 성립하지 않으면 뒤 단계는 애초에 의미가 없습니다.

### 근거

- **장애 복구의 비용은 "왕복 횟수"**입니다. 고치고 → 재기동하고 → 또 안 되고를 반복하는 것이 가장 비쌉니다. 한 번에 고쳐야 할 것을 전부 보여주는 편이 낫습니다.
- 통과한 단계의 로그도 남깁니다. **"무엇이 문제가 아닌지"를 아는 것 역시 디버깅**이기 때문입니다. "포트는 열려 있다"를 확인하면 그 방향은 더 안 봐도 됩니다.
- 각 단계에 **실제로 확인한 값**(양쪽 네트워크 목록, EXPOSE 포트, 환경변수)을 함께 남깁니다. 사용자가 도구의 판단을 그대로 믿지 않고 눈으로 검증할 수 있어야 합니다. 틀렸을 때 틀렸다는 걸 알 수 있는 도구가 신뢰할 수 있는 도구입니다.
- 원인을 **못 찾았을 때도 결과입니다.** 모든 단계를 통과하면 "네트워크 레벨에는 원인이 없다"고 말하고, 다음으로 확인할 것(애플리케이션 리슨 여부, 인증 실패, `DOCKER-USER` 체인)을 안내합니다. 이것만으로도 탐색 범위가 절반으로 줄어듭니다.

## 그 밖의 결정들

위만큼 길게 쓸 정도는 아니지만, 이유가 있어 그렇게 한 것들입니다.

### 판정

| 결정 | 이유 |
|------|------|
| `daemon.json`이 없으면 Docker 기본값으로 판정 | 파일이 없는 호스트가 가장 흔하고, 그 상태의 기본값 대부분이 취약합니다. "파일 없음 = 통과"는 거짓 안심을 줍니다. |
| 잘못된 타입은 FAIL이 아닌 WARN | `"icc": "false"`는 취약하다기보다 **dockerd가 시작되지 않을 수 있는** 설정 오류입니다. 성격이 달라 따로 표시합니다. |
| host 네트워크 · 특권 포트는 '취약'이 아닌 '주의' | 성능 · 멀티캐스트 · 웹 표준 포트처럼 정당한 사용처가 많습니다. 금지가 아니라 검토를 요청하는 것이 실무에 맞습니다. |
| compose 결과는 "파일 × 룰" 단위로 묶음 | 서비스 10개에 `read_only`가 없다고 감점이 10번 되면 점수가 의미를 잃습니다. 룰 단위로 한 번 감점하고 영향받는 서비스는 목록으로 보여줍니다. |
| CIS 근거를 v1.6.0 번호로 통일 | CIS 벤치마크는 버전마다 항목 번호가 바뀝니다(icc: 이전 버전의 2.1 → v1.6.0의 2.2). 교육용 도구의 근거는 검증 가능해야 합니다. |
| 네트워크 룰은 설정 파일보다 **실행 중인 상태**를 우선 | 설정 파일에 적힌 것과 실제로 떠 있는 것은 다를 수 있습니다(수동 `docker run`, 임시 `network connect`). 장애는 실제 상태에서 일어납니다. icc도 Docker가 bridge에 기록한 값을 먼저 봅니다. |
| compose `depends_on`을 의존성으로 자동 추론 | 선언 파일을 쓰지 않아도 기본 검증이 되게 합니다. 단, 이 호스트에서 실행 중인 프로젝트만 대상으로 해 다른 서버용 compose 파일로 오탐하지 않습니다. |
| NET-004는 Docker가 없으면 compose 파일로 대체 판정 | 민감 포트 노출은 가장 흔한 사고 경로라, 실제 상태를 볼 수 없을 때도 확인할 수 있는 만큼은 확인합니다. |
| override 병합은 `docker compose` 규칙을 따름 | 자동 탐색에서는 override를 병합하고, `-f`로 파일을 지정하면 병합하지 않습니다. 실제 배포 동작과 판정이 어긋나지 않게 하기 위해서입니다. |

### 수집과 출력

| 결정 | 이유 |
|------|------|
| 수집 실패를 예외가 아니라 컨텍스트에 기록 | "권한이 없어서 못 읽었다"도 사용자에게 유용한 진단 결과입니다. 크래시 대신 이유를 보여줍니다. |
| Docker에 연결 못 하면 룰마다 '건너뜀'을 남김 | 조용히 결과를 빼면 "네트워크는 문제없음"으로 오해합니다. 점검하지 못했다는 사실 자체를 표에 드러냅니다. |
| SDK · CLI · 스냅샷이 같은 `docker inspect` JSON을 공유 | 수집 경로가 셋이어도 파서는 하나라 동작이 일관되고, 테스트는 가짜 inspect JSON만 넣으면 됩니다. |
| 시크릿 값은 절대 출력하지 않음 | 보안 점검 리포트가 새로운 유출 경로가 되면 안 됩니다. 변수 이름만 보여주고, 테스트로 값이 출력되지 않음을 검증합니다. 진단이 환경변수를 읽을 때도 비밀번호 계열 키는 아예 읽지 않고, URL에 섞인 자격증명은 가립니다. |
| HTML 리포트는 외부 리소스 없이 한 파일로 | 서버에서 만든 리포트를 메일로 보내거나 인터넷이 없는 곳에서 열어도 똑같이 보여야 합니다. 웹 폰트 대신 시스템 폰트를 씁니다. |
| 리포트의 Markdown은 원문 HTML을 허용하지 않음 | `dependencies.yaml`의 이유 문구처럼 사용자 입력이 섞입니다. 공유되는 리포트가 스크립트 실행(XSS) 경로가 되지 않도록 테스트로 검증합니다. |
| JSON을 stdout으로 낼 때 나머지 출력은 stderr로 | `dockguard scan --format json \| jq`가 항상 동작하도록, 진행 표시 · 안내 · `--fail-on` 경고가 JSON에 섞이지 않게 합니다. |
| 설명 텍스트를 Markdown으로 작성 | 터미널(rich)과 HTML 리포트에서 같은 원문을 렌더링하고, 코드 블록을 복사하기 쉽게 보여줄 수 있습니다. |
| 설명 텍스트 품질을 테스트로 검사 | 룰과 학습 주제의 설명이 130개가 넘습니다. `**강조(괄호)**에` 같은 한국어 Markdown 함정을 사람이 찾기는 어려워, 전부 렌더링해 보고 남은 `**`를 잡아냅니다. |
